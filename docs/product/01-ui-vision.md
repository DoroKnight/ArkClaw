# ArkClaw UI Vision

> 文档类型：Product Design / UX Vision  
> 适用范围：ArkClaw 后续全部 UI、交互与视觉设计  
> 产品阶段：上位原则定义  
> 本文不包含：代码、Qt 实现、文件架构、TDD、详细 Screen Specification

## 0. 文档目的与约束效力

本文定义 ArkClaw UI 的产品定位、体验目标、交互层级与设计边界，是后续 interaction model、screen specification、visual system 和实现方案的上位约束。

后续设计若与本文冲突，必须先修订并重新确认本文，而不能在下位文档或实现中绕过。本文没有明确决定的事项统一标记为 `Unknown / To Be Designed`；该标记表示尚未获得产品授权，不得被原型、视觉稿或实现默认为既定行为。

本文中的规范词含义如下：

- **必须（Must）**：不可违反的产品约束。
- **应该（Should）**：默认遵循；偏离时必须说明理由并经过评审。
- **可以（May）**：允许探索，但不代表功能已经确认。
- **`Unknown / To Be Designed`**：尚未决定，必须在进入实现前完成设计与验证。

### 0.1 产品定位

ArkClaw 是以桌面角色为主要入口的 **Desktop Agent（桌面智能体）**，不是普通桌宠、传统聊天软件或常驻控制台。

它的长期价值是让用户通过自然语言委托任务，由 Agent 在得到适当授权后调用桌面应用、文件和工具；界面只在需要沟通、决策或承载任务内容时出现。Schwarz 既是角色，也是用户理解 Agent 是否存在、正在做什么、是否需要介入的主要视觉载体。

### 0.2 核心 UI 目标

> **以尽可能小的桌面占用，让用户自然地发起、理解并控制一个能够行动的 Desktop Agent，同时保持 Schwarz 的角色连续性、操作可信度与桌面安静感。**

这一目标包含三项不可分割的要求：

1. **能力可达**：用户能够迅速开始对话、选择动作，并在复杂任务中获得足够的工作空间。
2. **行为可理解**：Agent 的状态、当前任务与等待原因可被用户感知，而不是隐藏在不可见的后台过程里。
3. **存在不过度**：Agent 的能力不以常驻窗口、工具栏或信息面板证明；不需要 UI 时，桌面只保留 Schwarz。

成功不以“显示了多少功能”衡量，而以用户能否在不被打扰、不失去控制、不中断既有桌宠体验的前提下完成任务衡量。

## 1. Schwarz 在 UI 中的角色

### 1.1 主要入口，而非装饰性吉祥物

Schwarz 是 ArkClaw 的 **Home、入口、状态载体与空间锚点**：

- **Home**：默认桌面状态只显示 Schwarz；关闭临时 UI 即回到 Schwarz。
- **入口**：用户从 Schwarz 发起轻量对话或上下文动作，而不是先寻找应用主窗口。
- **状态载体**：角色动画、姿态与邻近的轻量反馈共同表达 Agent 状态。
- **空间锚点**：按需出现的轻量表面应与 Schwarz 保持可理解的来源关系。
- **身份载体**：视觉语言应体现 Schwarz 的冷静、克制、精准与有限温度，而不是套用通用 AI 品牌外观。

Schwarz 不是把功能入口堆在角色周围的快捷启动器，也不是持续播放无关动画的状态灯。角色表达必须服务于可理解性与陪伴连续性，不能牺牲桌面可用性。

### 1.2 Agent 状态语言

以下七种状态构成全局语义词汇。角色表现与 UI 表现必须表达同一事实，不能各自维护互相矛盾的状态。

| 状态 | 用户应理解的含义 | 表达原则 |
|---|---|---|
| `Idle` | Agent 可用，当前没有需要用户关注的任务 | 安静、低强度；不因空闲自动展开 UI |
| `Listening` | Agent 正在接收用户输入 | 明确但克制；必须让用户知道输入是否仍在被接收 |
| `Thinking` | Agent 正在组织方案或判断下一步 | 表达处理中，不伪装成已经执行 |
| `Acting` | Agent 正在调用应用、文件或工具执行任务 | 必须与 `Thinking` 区分；高影响行动需要清晰的控制与授权语义 |
| `Waiting` | 任务因用户输入、授权、外部条件或时间而暂停 | 必须说明在等什么；不能伪装为仍在工作 |
| `Success` | 当前任务或阶段已成功完成 | 适度、短暂、可确认；随后回归安静状态 |
| `Error` | 当前任务或阶段无法按预期继续 | 可识别、可恢复；不使用惊吓式动画或持续警报制造压力 |

各状态对应的具体动画、持续时间、声音、颜色及无动画替代方案均为 `Unknown / To Be Designed`。

### 1.3 角色与 UI 的职责边界

- Schwarz 负责存在感、入口和状态概览。
- 按需 UI 负责语言、选择、确认、内容与可恢复操作。
- 复杂信息不能压缩成难以理解的角色动作。
- 简单状态不能为了“显得强大”而强制展开完整界面。
- 角色动画不能替代必要的文字说明、权限确认或错误恢复路径。

## 2. UI 何时出现

UI 只有在其信息价值或操作价值高于桌面干扰时才应出现。

### 2.1 用户主动召唤

- 默认桌面只显示 Schwarz。
- **已确认产品意图**：用户左键双击 Schwarz，打开轻量级 `Conversation Capsule`，而不是完整 Console。
- **已确认未来方向**：用户右键 Schwarz，使用与角色锚定的 `Anchored Action Palette`，而不是传统 Windows 菜单。
- 任何其他鼠标、键盘、语音或系统级召唤方式均为 `Unknown / To Be Designed`。

“双击打开 Capsule”确认的是产品语义，不代表输入仲裁机制已经解决。现有桌宠的左键单击、拖拽和右键行为必须继续成立；具体冲突见第 6 节的硬约束。

### 2.2 Agent 请求用户介入

当 Agent 无法安全、正确或有授权地继续时，可以出现与当前任务相称的最小 UI，例如：

- 需要用户补充缺失信息；
- 需要用户在清晰选项间做决定；
- 需要用户确认高影响或不可轻易撤销的行动；
- 发生可恢复错误，且仅靠角色状态不足以说明恢复方法；
- 任务结果需要阅读、比较或继续操作。

Agent 状态发生变化本身，不自动构成展开 UI 的理由。`Thinking`、`Acting`、`Success` 等状态优先由 Schwarz 和低干扰反馈表达；只有用户确实需要信息或控制时才增加界面层级。

### 2.3 任务复杂度增长

当当前任务超出轻量对话表面的承载能力时，`Conversation Capsule` 可以连续扩展为 `Agent Workspace`。扩展应由内容和任务需求驱动，而不是由功能分类或产品宣传驱动。

触发 Workspace 的精确复杂度标准、用户是否需要显式确认扩展，以及不同任务类型的最小承载要求均为 `Unknown / To Be Designed`。

## 3. UI 何时消失

### 3.1 应消失或收拢的情况

UI 应在以下情况下回到更轻的层级，最终恢复“仅 Schwarz”的默认桌面：

- 用户明确关闭、收拢或结束当前交互；
- 简单任务已经完成，结果已被用户看见，且没有待处理输入；
- 临时动作选择已经完成，且继续显示不会提供额外价值；
- 用户将任务交给 Agent 后，任务可在后台安全继续，当前无需持续阅读或控制；
- 任务被取消，且没有需要保留的恢复信息。

收拢时必须保持任务连续性：从 Workspace 回到 Capsule、再回到 Schwarz，不应被用户理解为任务被清空、会话丢失或 Agent 被终止。

### 3.2 不应自动消失的情况

UI 不得在以下情况下无提示消失：

- 正在等待用户授权、输入或选择；
- 存在未提交内容或用户正在阅读关键结果；
- 高影响行动仍在进行，且用户需要中止、查看范围或理解后果；
- 错误尚未解释，恢复路径尚未呈现；
- UI 消失会让用户误以为任务已经完成、失败或停止。

自动收拢的时间规则、失焦行为、跨显示器行为、窗口层级与重新打开后的恢复位置均为 `Unknown / To Be Designed`。

## 4. Conversation、Action 与 Workspace 的关系

三者不是三个并列应用，也不是传统侧边栏中的三个页面。它们是同一个 Agent 交互在不同意图和复杂度下的三种承载层级。

| 层级 | 核心问题 | 主要形态 | 约束 |
|---|---|---|---|
| `Conversation` | “我想让你理解并帮助我。” | 由 Schwarz 打开的轻量 `Conversation Capsule` | 自然语言优先；不以长期消息列表定义产品 |
| `Action` | “此刻我可以让你做什么，或需要决定什么？” | 与 Schwarz 或当前上下文锚定的 `Anchored Action Palette` / 决策表面 | 上下文相关、短暂、少量选择；不是永久工具栏 |
| `Workspace` | “这个任务需要更多空间来查看、组织和控制。” | 由 Capsule 连续扩展的 `Agent Workspace` | 保留会话与任务上下文；不能退化为 Dashboard 或 IDE Shell |

### 4.1 统一任务连续性

- Conversation 是主要交互协议，不等同于“聊天页面”。
- Action 是对当前意图的快捷表达或必要决策，不与 Conversation 争夺主入口。
- Workspace 是复杂度的扩展，不是另起一个与角色割裂的主程序。
- 三者必须共享同一任务状态、权限语义和 Agent 状态。
- 升级与降级必须可理解、可逆，并保持内容与操作上下文。
- 相同操作不应同时散落在 Capsule、Palette 与 Workspace 中形成互相竞争的入口。

### 4.2 概念级转换关系

```text
Schwarz
  ├─ 主动对话意图 → Conversation Capsule
  │                    └─ 任务复杂度增加 → Agent Workspace
  └─ 上下文动作意图 → Anchored Action Palette
                       └─ 需要解释或复杂处理 → Conversation / Workspace

任一临时表面完成其职责后 → 逐级收拢 → Schwarz
```

具体尺寸、位置、组件、导航、布局和动画参数不属于本文范围，均应在后续文档中设计。

## 5. Progressive Disclosure 与 UI on Demand

ArkClaw 必须披露**任务当前所需的复杂度**，而不是一次展示产品拥有的全部能力。

1. Schwarz 表达存在与状态。
2. Capsule 承载一句请求、一次澄清或短结果。
3. Action Palette 承载少量、当前可执行的上下文动作。
4. Workspace 只在任务确实需要持续内容、多步控制或更大阅读面积时出现。
5. 技术详情、执行记录与诊断信息只有在用户需要理解问题或主动展开时才出现。

每增加一层 UI，都必须回答：为什么 Schwarz 本身不足、为什么更轻的表面不足、用户何时能够安全退出。无法回答时，不得升级界面。

## 6. 鼠标交互兼容性：不可破坏的不变量

### 6.1 硬约束

> **任何未来由鼠标触发的 UI 交互，都不得与现有桌宠鼠标交互或手势冲突。**

任何新 UI 手势不得静默窃取（steal）、重新解释（reinterpret）、遮蔽（shadow）或延迟到改变体感的程度。只要存在歧义，该交互就必须保持为 `Unknown / To Be Designed`，不得以“常见平台行为”为理由直接实现。

### 6.2 当前必须保护的输入基线

依据当前项目行为，至少必须保护：

| 现有输入 | 既有语义 | 保护要求 |
|---|---|---|
| 左键单击 Schwarz | 触发一次 `Interact` | 新手势不得吞掉、重复或无提示延迟该动作 |
| 左键按住并移动超过系统拖拽阈值 | 拖动桌宠；释放后进入既有下落/落地流程 | 新 UI 不得抢占指针序列、改变拖拽阈值或造成位置跳变 |
| 右键 Schwarz | 打开现有桌宠动作菜单 | 未来 Palette 必须在能力与可达性获得确认后显式替换，不能让右键失效或产生双重菜单 |
| 透明区域与可见角色像素的既有命中规则 | 可交互像素接收输入，无效区域不应阻挡桌面 | 新表面不得扩大隐形阻挡区或破坏点击穿透 |
| 已开始的有效指针序列 | 在动画变化或跨越窗口后仍应获得一致的结束语义 | UI 展开、收拢或状态变化不得留下卡住的按下/拖拽状态 |

基线发生变化时，必须以当前可验证实现和已确认产品决策为准更新本表，不能凭旧文档推断。

### 6.3 双击与单击的未决冲突

左键双击打开 `Conversation Capsule` 是已确认方向，但它与“单击触发 `Interact`”共享同一输入序列。以下问题尚未决定：

- 第一次单击应立即触发 `Interact`，还是等待双击判定；
- 若先触发 `Interact`，第二次单击如何避免重复动作或产生错误反馈；
- 为识别双击引入的等待是否会破坏现有单击响应感；
- 双击过程中轻微移动、跨越拖拽阈值、丢失捕获或角色动画改变时如何仲裁；
- 双击命中区域是否完全沿用现有角色像素命中规则。

以上统一标记为 `Unknown / To Be Designed`。在完成明确的手势优先级、取消语义、反馈规则与回归验收前，不得把双击入口视为可直接实现的规格。

### 6.4 鼠标设计门禁（Design Gate）

任何新增或变更的鼠标触发交互，进入详细设计或实现前必须同时满足：

1. 已记录并在当前版本验证所有受影响的既有手势。
2. 已定义新旧手势的识别条件、优先级、超时、阈值、取消与失败路径。
3. 已证明单击、拖拽、右键、命中测试与指针序列连续性没有回归。
4. 冲突时有显式产品决策，不依赖框架默认事件顺序。
5. 用户能够理解结果；同一物理动作不会因难以观察的条件产生意外语义。
6. UI 出现与消失不会让桌宠留在错误动作、错误位置或未结束的输入状态。

任一项不满足，设计评审结论必须为不通过。

## 7. Agent State Visible，但不过度暴露系统

状态可见的目标是建立信任，不是把内部执行过程变成开发者控制台。

- 用户必须知道 Agent 是在接收、思考、执行、等待、完成还是失败。
- `Thinking` 与 `Acting` 必须有清晰语义差异，避免把未执行的计划误认为已执行。
- `Waiting` 必须指出等待对象或用户下一步，而不是无限加载。
- 复杂任务的状态应在当前表面中就近表达；不为状态专门常驻一个面板。
- 默认不显示模型名称、Token、内部工具调用参数、线程、日志、堆栈或开发者生命周期细节。
- 当技术信息确实有助于诊断时，应按需展开，并与普通用户表述分层。
- 权限、风险和可撤销性不能只靠角色动画表达。

状态与 Schwarz 动画、文字反馈、任务进度之间的映射为 `Unknown / To Be Designed`。

## 8. Google Gemini 与 Material 3 / Material 3 Expressive 的借鉴边界

### 8.1 应借鉴的原则

ArkClaw 借鉴的是交互语言与视觉层级方法，而不是 Google 的品牌外观。

1. **以用户意图为起点**：像 Gemini 的对话式入口一样，让用户先表达目标，再按需显现工具和结构。
2. **内容优先、Chrome 最少**：让请求、结果与当前决策成为视觉中心，减少长期导航和应用边框。
3. **用尺寸、形状与容器建立优先级**：Material 3 Expressive 使用 color、shape、size、motion 与 containment 引导注意力；ArkClaw 应将其用于突出当前最重要的信息或行动，而非装饰。
4. **Meaningful Motion（有意义的动效）**：动效说明对象从何处出现、如何关联、状态为何变化。Capsule 扩展为 Workspace 时，应保持空间与任务连续性。
5. **Fluid Container Transformation（流体容器转换）**：表面在轻量与复杂形态间连续转换，避免突然打开一个与 Schwarz 无关的独立大窗口。
6. **Dynamic Surfaces（动态表面）**：界面面积、信息密度与控制数量响应当前任务，而不是长期固定。
7. **表达服务于可用性**：视觉个性必须帮助注意力、分组与状态理解；不能以“更有表现力”为理由牺牲清晰度。
8. **可访问与可调节**：保持清晰对比、可识别状态、可替代的非动画信息，并尊重 Reduced Motion 等用户设置。
9. **一致但不等于统一外观**：复用原则与行为逻辑，同时允许 ArkClaw 形成独立的角色品牌语言。

Google 对 Material 3 Expressive 的公开说明强调以色彩、形状、尺寸、动效和容器关系提升注意力与可用性，同时要求从用户需要出发、优先保证功能并遵守可访问性标准；Material 的品牌指导也明确支持产品通过自身色彩、图形、字体、语气与动效形成独立身份。本文据此采用“原则迁移、品牌重建”的方式，而非视觉复刻。

### 8.2 不得直接照搬的视觉元素

- Google 四品牌色及其组合逻辑。
- Gemini 的蓝紫渐变、星芒标志、光晕和品牌动效。
- Gemini 现有页面布局、输入框比例、欢迎区、建议卡片或消息排版。
- Material 组件的默认圆角、阴影、色彩 Token、字体和图标风格。
- Android / Mobile First 的导航结构、FAB、底部导航或触控页面密度。
- 以大量圆角卡片、彩色胶囊和浮动工具条制造“Material 感”的表面模仿。
- 与 Schwarz 气质无关的高饱和、活泼、弹跳或庆典式表达。
- 任何让 ArkClaw 看起来像 Google 产品换皮的命名、构图或视觉资产。

ArkClaw 的具体色彩、字体、形状、图标、动效曲线、材质与角色视觉比例均为 `Unknown / To Be Designed`。后续视觉系统必须从 Schwarz 的角色身份、桌面环境与可访问性共同推导。

## 9. 必须避免的产品与视觉方向

### 9.1 产品形态禁区

- **Admin Dashboard**：用数据卡、统计面板和管理导航组织 Agent。
- **IDE-style Sidebar**：用永久侧边栏、树状结构、面板坞站定义主要体验。
- **Traditional Chat App**：以常驻消息列表、会话列表和永久输入框定义产品。
- **永久 Console / Control Center**：要求用户先打开主窗口才能使用 Agent。
- **功能启动器堆叠**：把大量快捷按钮长期挂在 Schwarz 周围。

### 9.2 视觉禁区

- Gaming HUD、准星、战斗读数、装备框或任务雷达。
- Cyberpunk UI、霓虹描边、故障效果、全屏网格和过度科幻装饰。
- 大面积无语义渐变、Glow、玻璃拟态或装饰性粒子。
- 用夸张动画持续吸引注意力，破坏 Calm Desktop。
- 通过密集状态、日志和技术参数证明 Agent 正在工作。
- 直接复制 Google / Gemini / Material 的品牌色、布局或组件外观。

### 9.3 交互禁区

- 永久工具栏、永久输入框、永久状态栏。
- 未经请求自动展开完整 Workspace。
- 在没有信息价值时用通知、浮层或角色动画打断用户。
- 同一动作在多个表面重复出现，造成入口竞争。
- 不可逆地从轻量表面跳入大型窗口，或关闭 UI 就丢失任务上下文。
- 任何未经门禁验证、会冲突或可能冲突的鼠标手势。

## 10. Design Principles

以下原则是所有后续设计评审的检查标准。

### 1. Character First — 角色是 Home

Schwarz 是默认状态、主要入口和 Agent 身份中心。任何 UI 都应像从角色与当前任务自然生长出来，而不是覆盖角色另起一套产品。

### 2. Conversation First — 意图先于导航

自然语言是主要交互协议。用户应先表达目标，再看到完成目标所需的结构；不能要求用户先理解功能分类和页面层级。

### 3. UI Must Earn Its Presence — UI 必须证明出现的必要性

只有当界面能提供 Schwarz 无法独立承载的信息、选择或控制时才出现，并使用能完成任务的最小形态。

### 4. Progressive Disclosure — 只展开当前需要的复杂度

从 Schwarz 到 Capsule，再到 Workspace，复杂度逐级增加。不得一次展示全部能力，也不得为了简单任务打开完整工作区。

### 5. One Task, Continuous Surfaces — 同一任务保持连续

Conversation、Action 与 Workspace 必须共享上下文、状态和权限语义。形态变化不应让用户重新开始、重新定位或猜测任务是否仍在继续。

### 6. Agent State Visible — 状态可见且诚实

Idle、Listening、Thinking、Acting、Waiting、Success、Error 必须可区分。系统不能把等待伪装成思考、把计划伪装成执行，或把失败隐藏在持续动画中。

### 7. Pet Gestures Are Protected — 桌宠手势不可回归

所有现有鼠标交互均受保护。任何新 UI 手势只有在完成冲突设计、显式决策与回归验证后才可成立；歧义不是实现细节，而是阻断项。

### 8. Motion Explains Change — 动效用于解释变化

动效应表达来源、关系、状态与连续性。不得用动效掩盖等待、制造虚假进度或持续争夺注意力。

### 9. Calm Is a Functional Requirement — 安静是功能要求

Calm Desktop 不只是审美偏好。完成、收拢、后台继续和无事发生时，界面必须主动降低存在感，让用户重新拥有桌面。

### 10. Expressive, Not Imitative — 有角色表达，不做品牌模仿

借鉴 Material 的层级、容器和动效原则，但视觉必须由 ArkClaw / Schwarz 的身份建立。表达应克制、准确、有温度，不复制 Google，也不滑向游戏 HUD 或赛博朋克。

### 11. Trust Before Spectacle — 信任优先于奇观

涉及桌面应用、文件和工具的行动，必须让用户理解 Agent 正在做什么、为何需要介入以及如何停止或恢复。视觉惊喜不能取代权限与后果说明。

### 12. Unknowns Stay Visible — 未决问题不得被隐藏

凡未确认的触发方式、行为、视觉 Token、权限流程或状态映射，必须标记 `Unknown / To Be Designed`。原型中的临时选择不能自动升级为产品决定。

### 13. Accessible by Design — 可访问性从概念阶段开始

信息不能只依赖颜色、动画或角色姿态。后续设计必须提供清晰文字、可辨识焦点、足够对比、Reduced Motion 支持，以及与鼠标等价的可访问操作路径；具体方案为 `Unknown / To Be Designed`。

---

## 11. 目标桌面体验

ArkClaw 最终应让用户感到：桌面上不是常驻着一套软件界面，而是有一个安静、可理解、能够行动的角色在身边。

平时，Schwarz 自然地存在，不要求注意力。用户需要帮助时，可以从角色直接开始说出目标；简单事情在轻量表面中完成，复杂事情才连续展开为足够的工作空间。Agent 思考、行动、等待、成功或失败都有诚实而克制的反馈。任务结束后，界面自然收拢，桌面重新安静下来，但任务连续性与信任不会消失。

理想体验不是“打开 ArkClaw、寻找功能、操作界面、关闭应用”，而是：

> **看见 Schwarz，表达意图，理解 Agent，必要时介入，然后自然回到自己的桌面。**

## 12. Unknown / To Be Designed Register

以下事项尚未决定，后续必须单独设计和确认：

1. 双击打开 Capsule 与现有单击 `Interact` 之间的完整事件仲裁。
2. 双击超时、移动容差、拖拽阈值、取消与反馈规则。
3. `Anchored Action Palette` 替换现有右键菜单的迁移方式、能力对等与失败回退。
4. Capsule、Palette 与 Workspace 的准确位置、尺寸、显示器边界和窗口层级。
5. UI 失焦、自动收拢、后台继续、重新打开与任务恢复规则。
6. 何种任务复杂度允许或要求 Capsule 扩展为 Workspace。
7. Agent 主动请求用户介入的优先级、频率与通知边界。
8. Idle、Listening、Thinking、Acting、Waiting、Success、Error 对应的角色动画、文字、色彩、声音与无动画替代。
9. 桌面应用、文件和工具调用的权限、确认、撤销与执行范围表达。
10. 键盘、辅助技术、语音或其他非鼠标入口及其与 Character First 的关系。
11. ArkClaw / Schwarz 的正式色彩、字体、形状、图标、材质与动效系统。
12. Schwarz 角色素材在产品中的使用、修改与分发授权边界。

在这些事项得到确认前，任何下位文档都不得通过具体控件或原型行为替代产品决策。
